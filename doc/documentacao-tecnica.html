01

Visão geral do sistema

A Captação Movida é uma plataforma de captação de leads: vendedores cadastram clientes através de um formulário; gestores veem todas as captações, com busca e exportação em CSV. O papel de cada usuário vem do Clerk, no claim app_role do session token (nunca no claim role, que pertence ao Supabase e vale sempre authenticated).

O fluxo de um lead sempre segue a mesma regra, para nunca perder um cadastro:

Formuláriovendedor preenche
→
INSERT em captacoesSupabase, fonte da verdade
→
Database Webhookdispara sozinho no INSERT
→
Destinos externosCRM + Google Sheets

Nesta rodada de trabalho, um segundo produtor de linhas na tabela captacoes foi adicionado além do formulário do vendedor: o job vianuvem-import/, que importa leads de um sistema de terceiros de hora em hora (seção 6). Ele reaproveita exatamente o mesmo pipeline de saída (Database Webhook → Google Sheets) sem que nada nesse pipeline precisasse mudar.

02

Tela de login

A tela de login (src/components/login/) foi ajustada para ficar fiel ao Figma:

  • Borda neon do cartão: substituída a versão recriada em CSS por uma imagem real fornecida pelo design (public/login/card-border.png), limpa de artefatos de transparência (alpha "despremultiplicado" sobre fundo preto) e, na segunda rodada, refeita a partir de um arquivo de origem mais limpo enviado pelo usuário.
  • Campos do formulário menores que no Figma: causa raiz era o padding do .card em unidades % — como o elemento é position: absolute, a porcentagem resolve contra o containing block (o palco inteiro), não contra o próprio elemento. Corrigido trocando para unidades cqw (container query width), que resolvem contra o container real do cartão.
  • Verificação do mobile: conferido que a correção acima não quebrou a versão mobile (que já esconde a borda/elementos decorativos via media query). Um problema pré-existente e não relacionado foi encontrado — a classe .tlArt tem um espaçamento estranho no mobile — mas não foi corrigido porque está fora do escopo desta mudança e não foi confirmado com o usuário.
Resolvido em 11/07/2026

O bug do .tlArt no mobile foi corrigido: a causa era a media query mobile esconder todas as camadas decorativas (.bgPlate, .coin, .logos...) mas ter esquecido o .tlArt na lista — a imagem ficava flutuando sobre o layout. Adicionado à regra display: none e verificado com screenshot em 375px (limpo) e 1440px (arte intacta). Ver seção 18.

04

Integração com Google Sheets

Cada captação passou a ser replicada em uma de 3 planilhas reais do Google Sheets (uma por gestor/loja), usando um Google Apps Script publicado como Web App como destino de um segundo Database Webhook na mesma tabela captacoes — o Supabase dispara para os dois destinos (CRM principal + Apps Script) de forma independente.

Roteamento por loja

Para decidir em qual planilha uma captação cai, o campo publicMetadata.loja (definido por um admin no Clerk, o vendedor não escolhe) é propagado até o payload do webhook e usado pelo script para resolver a planilha certa:

publicMetadata.lojaClerk, por vendedor
→
captacoes.lojacoluna no Supabase
→
LOJA_PARA_PLANILHAmapa normalizado no Apps Script
→
1 de 3 planilhaseverton / wesley / william

Arquivo: supabase/webhooks/captacoes-to-google-sheets.gs. Estrutura principal:

  • PLANILHAS — IDs das 3 planilhas reais.
  • LOJA_PARA_PLANILHA — mapa normalizado (maiúsculas/acentos não importam), incluindo aliases reais descobertos durante os testes (ex.: variações do nome "Campinas Shopping Dom Pedro").
  • doPost(e) — valida um segredo compartilhado, resolve a planilha e adiciona uma linha.
  • registrarErro — loga falhas (ex.: loja sem planilha mapeada) numa aba própria, nunca logando dado pessoal, só o id da captação.

Colunas em cada planilha: DATA | VENDEDOR | LOJA | NOME | CELULAR | E-MAIL | CPF | PLACA | STATUS. E-MAIL e CPF só vêm preenchidos para captações de origem vianuvem (seção 6); do formulário do vendedor, ficam em branco.

Segredo do webhook (configuração manual necessária)

A autenticação entre Supabase e o Apps Script é um segredo simples passado por query string na própria URL do webhook — não um header, e não OAuth. Isso já causou um incidente real (erro "segredo inválido ou ausente" por esquecimento na hora de configurar):

  1. No Apps Script: ⚙️ Configurações do projeto → Propriedades do script → propriedade WEBHOOK_SECRET com um valor aleatório (ex.: openssl rand -hex 16).
  2. No Supabase: a URL do webhook precisa terminar em ?secret=<mesmo valor>.
  3. Os dois lados (Apps Script e URL do Supabase) precisam ficar sempre sincronizados manualmente — não há rotação automática.

Implantação (resumo)

O passo a passo completo está no cabeçalho do próprio arquivo .gs. Resumo:

  1. Projeto Apps Script standalone (não vinculado a nenhuma planilha específica, porque escreve em 3 arquivos diferentes).
  2. Rodar setupSheet() uma vez, para criar a aba de log de erro.
  3. Configurar WEBHOOK_SECRET (acima).
  4. Implantar como Web App ("Executar como: Eu", "Quem pode acessar: Qualquer pessoa").
  5. Criar o Database Webhook no Supabase apontando pra URL gerada + ?secret=....

06

Importação automática ViaNuvem/Unico Auto

Esta é a peça mais nova e mais complexa desta rodada: um job standalone, vianuvem-import/, que faz login automatizado no sistema de terceiros ViaNuvem/Unico Auto (usado pelas lojas para gestão de processos de financiamento/consórcio de veículos), exporta os "Processos que atuo" e insere os novos como leads em captacoes, de hora em hora.

Decisões de projeto (e por quê)

DecisãoMotivo
Dedupe por placa, em toda a tabela, qualquer origem Evita duplicar lead do mesmo veículo, mesmo que já tenha vindo do formulário do vendedor. Trade-off aceito conscientemente: se o mesmo carro for revendido meses depois, o import vai pular esse veículo achando que já existe.
vendedor_id = "vianuvem" Identifica a origem do lead sem corresponder a nenhum usuário real do Clerk. Consequência das policies de RLS: esses registros só aparecem para o gestor, nunca para um vendedor específico — comportamento esperado.
Login via Playwright (não API oficial) Não existe (ainda) acesso de API documentado para o ViaNuvem. Login/senha simples, sem desafio de reCAPTCHA visível — apenas reCAPTCHA v3 (invisível, baseado em score). Nunca foi construída nenhuma automação para resolver/burlar um desafio de CAPTCHA explícito — isso foi uma restrição clara do usuário desde o início do projeto.
Deploy via Docker, não Node.js no host O servidor de produção não tinha Node.js instalado. A imagem oficial do Playwright já traz Chromium e todas as dependências de sistema — evita apt-get/sudo no host.
CPF e e-mail agora fazem parte do schema Uso real confirmado: preencher as colunas CPF/E-mail que as 3 planilhas gerenciais já tinham, mas que o formulário do vendedor nunca coletou.

Como o script funciona, passo a passo

1. LoginPlaywright preenche usuário/senha
→
2. Clica Exportar → Processosna página real, não via fetch externo
→
3. Baixa a planilhasignedURL da resposta capturada
→
4. Mapeia camposnome, CPF, e-mail, telefone, placa, loja
→
5. Dedupe + insertpor placa, vendedor_id = vianuvem

O passo 2 é a parte mais importante para entender: a primeira versão do script fazia login, extraía os cookies de sessão, fechava o navegador e chamava a API de exportação diretamente via fetch. Essa chamada era aceita pelo servidor mas devolvia um resultado vazio ({"fullSignedURL":"","async":false}), sem nenhum erro — o endpoint depende de algum contexto de sessão que só existe quando um clique real acontece na página, não apenas dos cookies. A correção foi deixar o próprio Playwright clicar em "Exportar" → "Processos" na página autenticada e escutar a resposta real que a SPA gera (função clicarExportarProcessos). Detalhes completos na seção 8.

ArquivoPapel

Mapeamento de colunas dinâmico

O relatório exportado do ViaNuvem tem colunas fixas (0–11, incluindo o estabelecimento/loja) seguidas de pares repetidos (rótulo, valor) a partir da coluna 12 — e o texto do rótulo muda conforme o "Tipo de Processo" de cada linha. Por isso o mapeamento não usa índice fixo de coluna para os campos dinâmicos (nome, CPF, e-mail, telefone, placa): ele varre cada linha procurando pelo texto do rótulo (extrairCamposDinamicos + acharCampoDinamico), com fallback de substring só depois de tentar igualdade exata — isso corrigiu um bug real onde a coluna "Estabelecimento" colidia com "ID Estabelecimento".

07

Deploy em produção

Sequência real executada no servidor supper-ubu01:

1. Build da imagem

cd captacao-movida/vianuvem-import
cp .env.example .env
chmod 600 .env
# preencher .env com usuario/senha do ViaNuvem e as chaves do Supabase
docker compose build

2. Teste manual

docker compose run --rm importer

Confirma no log a linha final Concluido: X importado(s), Y ja existente(s)/invalido(s). e confere no banco/planilha que os dados batem.

3. Instalar cron e logrotate

Gotcha real

O servidor Ubuntu era mínimo o suficiente para não ter cron nem logrotate instalados — tiveram que ser instalados manualmente antes de configurar o agendamento.

sudo apt update
sudo apt install -y cron logrotate
sudo systemctl enable --now cron

4. Crontab (do root, por causa do socket do Docker)

sudo crontab -e

# adicionar:
0 * * * * cd /home/supperadmin/captacao-movida/vianuvem-import && /usr/bin/docker compose run --rm importer >> /var/log/vianuvem-import.log 2>&1

Caminho do binário do Docker sempre absoluto (which docker) — o PATH do cron é muito mais curto que o de um shell interativo.

5. Rotação de log

sudo tee /etc/logrotate.d/vianuvem-import > /dev/null <<'EOF'
/var/log/vianuvem-import.log {
    daily
    rotate 14
    compress
    missingok
    notifempty
    copytruncate
}
EOF

copytruncate é necessário porque o cron sempre reabre o mesmo arquivo com >> — sem isso a rotação pode cortar um log no meio de uma execução.

Atualizar uma versão nova do job

git pull
docker compose build   # obrigatório - o Dockerfile copia o código pra imagem, não é volume
docker compose run --rm importer   # checagem manual antes de deixar o cron rodar sozinho
08

Histórico de bugs reais e correções

Ordem cronológica de tudo que quebrou de verdade durante a construção deste job, e como foi resolvido:

  • rede

    Timeout em networkidle

    Sintoma: page.goto estourava 30s de timeout. Causa: o site carrega pixels de rastreamento (Facebook, LinkedIn Ads, LaunchDarkly) que nunca param de fazer requisição — a rede nunca fica "idle" de verdade. Correção: trocado waitUntil: "networkidle" por "domcontentloaded".

  • infra

    npm: command not found no servidor

    Causa: Node.js não estava instalado no host. Decisão: ao invés de instalar Node diretamente (sugestão inicial), o usuário propôs usar Docker — adotado por ser mais limpo e por já vir com todas as dependências do Playwright.

  • infra

    Disco cheio (ENOSPC) durante docker compose build

    Diagnóstico: df -h / docker system df mostraram ~978MB de cache de build reaproveitável num disco de 9.8GB. Correção: sudo docker builder prune -f (liberou para 3.2GB livres) — evitado de propósito qualquer comando de limpeza mais agressivo sem antes mostrar o que seria removido, por ser servidor de produção.

  • runtime

    Node.js detected but native WebSocket not found

    Causa: o RealtimeClient do @supabase/supabase-js exige WebSocket nativo (Node 22+), mas a imagem usa uma versão mais antiga. Correção: dependência ws adicionada e passada explicitamente via createClient(url, key, { realtime: { transport: WebSocket } }).

  • login

    Popup nativo de permissão de geolocalização travando a página

    Como foi descoberto: o usuário rodou o script localmente com o navegador visível (VIANUVEM_HEADLESS=false) e viu ao vivo a caixa de permissão aparecer sem nada pra clicar "Permitir", travando a página até fechar sozinha. Correção: conceder a permissão programaticamente no contexto do Playwright antes de navegar — permissions: ["geolocation"] + coordenada fixa de São Paulo.

  • config

    Senha com # truncada em silêncio pelo .env

    Como foi descoberto: o próprio usuário percebeu que sua senha continha um # e associou ao comportamento do .env. Causa: sem aspas, o dotenv trata tudo depois de um # como comentário — a senha era cortada sem nenhum erro visível, apenas autenticando com um valor incompleto. Correção: documentado com destaque no .env.example e no cabeçalho do script — sempre envolver em aspas duplas valores com #, espaços ou aspas.

  • supabase

    Invalid API key ao checar/inserir no Supabase

    Diagnóstico: decodificado o JWT da SUPABASE_SERVICE_ROLE_KEY (só o payload, nunca a assinatura) e o campo role dentro dele acusava "anon", não "service_role". Correção: chave certa copiada de Project Settings → API no painel do Supabase.

  • export

    Exportação retornando vazia sem erro (fullSignedURL: "")

    Causa: a versão original replicava a chamada da API de exportação via fetch externo, usando os cookies extraídos após o login. O endpoint aceitava a chamada (sem erro HTTP) mas devolvia um resultado vazio — indício de que o servidor exige algum estado que só existe numa navegação real da UI. Correção: reescrito para o próprio Playwright clicar em "Exportar" → "Processos" na página autenticada, escutando a resposta real via page.waitForResponse (clicarExportarProcessos). Validado com sucesso após a mudança — fullSignedURL veio populado e o pipeline completo (download → parse → dedupe → insert) funcionou de ponta a ponta.

  • produção

    Login intermitente via cron ("ainda na tela de login"), mas funcionando manual

    Hipóteses descartadas com evidência: geolocalização (já resolvida programaticamente, idêntica em ambos os casos) e horário/fuso (o usuário confirmou que não era isso, e um dos disparos do cron às 2h da manhã funcionou normalmente, mostrando que não é sistemático). Causa real: o site responde mais devagar em alguns momentos, e o prazo de 10s para esperar o redirecionamento pós-login era curto demais — um login válido era erroneamente contado como falha. Correção: prazo aumentado de 10s para 30s. Sem custo para o caso comum (o script segue de qualquer forma assim que a URL mudar).

Estado atual

Pipeline completo validado em produção: login → clique em Exportar/Processos → download → parse → dedupe por placa → insert no Supabase → Database Webhook → planilha certa do Google Sheets, com CPF e e-mail preenchidos. Rodando via cron de hora em hora desde 08/07/2026.

09

LGPD

A importação automática do ViaNuvem trata dados de titulares que nunca interagiram diretamente com a Captação Movida — os dados já existiam em outro sistema, no contexto de um processo de financiamento de veículo. Isso muda a base legal aplicável em relação ao formulário do vendedor:

  • Base legal: legítimo interesse (art. 7º, IX), fundamentado no interesse comercial de dar continuidade a processos já iniciados nas próprias lojas — não consentimento direto com a Captação Movida.
  • Risco identificado e aceito conscientemente: o acesso à origem depende de login automatizado com credenciais de um usuário real do ViaNuvem, sem integração de API oficial nem acordo formal para esse tipo de extração. Recomendação de médio prazo: buscar API oficial (há indício de uma categoria de processo "TESTE API - USO EXCLUSIVO" na conta).
  • vendedor_id = "vianuvem": por consequência das policies de RLS, esses registros só ficam visíveis ao gestor — nunca a um vendedor específico.
  • Logs: nenhum processo deve logar nome, telefone, CPF ou e-mail em texto puro. Placa, quando necessária para diagnóstico, é mascarada (só os últimos 3 caracteres visíveis) via mascararPlaca.
  • Retenção do CPF: deve ter prazo igual ou mais curto que os demais campos — hoje seu único uso é preencher a planilha gerencial; a placa (não o CPF) é a chave de deduplicação.

Documento completo e atualizado: LGPD.md (seção 4.1 trata especificamente da origem ViaNuvem).

Pendências e próximos passos

  • Paginação do relatório ViaNuvem: ainda não testado com "Processos que atuo" além de algumas dezenas de linhas — se crescer para centenas, confirmar que o export continua trazendo tudo de uma vez.
  • Resposta assíncrona do endpoint de exportação: todos os testes reais vieram com async: false direto; a lógica de retry (MAX_TENTATIVAS, até 2 minutos) existe mas nunca foi exercitada de verdade.
  • API oficial do ViaNuvem/Unico Auto: vale abrir um chamado com o suporte perguntando por acesso oficial — a conta já tem uma categoria de processo "TESTE API - USO EXCLUSIVO", indício de que pode existir uma integração documentada, eliminando a dependência de login automatizado a médio prazo.
  • Alerta de falha do cron: MAILTO no crontab foi documentado como opção, mas depende de um MTA (sendmail/postfix) configurado no servidor — ainda não confirmado se existe.
  • Reivindicação de lead entre planilhas diferentes (seção 15): se a loja do vendedor que reivindica for de uma planilha diferente de onde a linha original do ViaNuvem está, o Apps Script não move a linha — só loga o erro. Caso raro, mas sem tratamento automático ainda.
  • Espaço em disco no servidor de produção tende a se repetir (já aconteceu 3x nesta rodada de trabalho) — considerar aumentar o volume ou automatizar limpeza periódica de imagens Docker não usadas.

Parte 2 — Autocadastro do vendedor

Sobre esta parte 2

Tudo abaixo foi construído numa rodada de trabalho posterior à primeira versão deste documento (seções 1–12). Mantém a mesma estrutura, só continuando a numeração.

A tela de login ganhou uma segunda aba, "Criar conta", para o vendedor se autocadastrar sem depender de um admin criar a conta manualmente no Clerk. Arquivos novos em src/components/login/: SignUpForm.tsx (o formulário) e clerkError.ts (tradução de erros do Clerk, ver seção 15). LoginScreen.tsx passou a controlar qual dos dois formulários (entrar/criar conta) é exibido.

Campos e fluxo

Por que loja/telefone não vão direto pro publicMetadata

O cliente (navegador) só pode escrever em unsafeMetadata no Clerk — nunca em publicMetadata, que é onde roleFromClaims/lojaFromPublicMetadata leem de verdade. Isso é proposital do Clerk: se o cliente pudesse escrever publicMetadata livremente, um vendedor mal-intencionado poderia se autopromover a gestor. Por isso o fluxo tem uma etapa a mais: depois que a conta é confirmada (passo 3), o formulário chama src/app/api/vendedor/perfil/route.ts — uma rota de servidor, com a CLERK_SECRET_KEY, que lê unsafeMetadata.loja/.telefone, valida contra LOJAS_DISPONIVEIS e um regex de telefone, e só então grava em publicMetadata. role nunca é escrito por essa rota — sem app_role definido, o app já trata como "vendedor" (menor privilégio).

Canal de origem e reivindicação de lead do ViaNuvem

Nova coluna canal em captacoes: "Indicação" quando o lead vem do formulário do vendedor (CapturaForm.tsx), "ViaNuvem" quando vem da importação automática (vianuvem-import/importar.mjs). Replicado na coluna CANAL das 3 planilhas.

O problema: mesma placa, duas origens

Pergunta que motivou esta seção: se o ViaNuvem já importou uma placa, e depois um vendedor de verdade cadastra "Nova Indicação" com essa mesma placa pelo portal, o sistema duplicava o lead? Sim — confirmado no código: CapturaForm.tsx fazia um INSERT direto, sem checar nada. Não há unique constraint em placa (só um índice normal), então nada impedia.

Comportamento decidido

SituaçãoComportamento
Placa nova (nunca vista)Insere normalmente, como sempre.
Placa já existe com vendedor_id = "vianuvem" Atualiza a linha existente: vira indicação do vendedor que cadastrou (vendedor_id/nome/telefone/loja mudam, canal vira "Indicação"). Não duplica.
Placa já existe com vendedor_id de outro vendedor de verdade Bloqueia com mensagem ("Essa placa já foi indicada por outro vendedor.") — nunca sobrescreve o lead de um colega.
ViaNuvem encontra placa já cadastrada (qualquer origem) Já era o comportamento existente: pula, não insere nem atualiza (dedupe do vianuvem-import, sem mudança nesta rodada).

Por que precisou de uma função no banco (RPC), não só RLS

A política de RLS de SELECT do vendedor só deixa ele ver as próprias captações. Isso significa que, do lado do navegador, o vendedor não consegue nem verificar se uma placa "de outro vendedor" existe — um UPDATE nessa linha simplesmente afeta 0 linhas, sem erro, do mesmo jeito que aconteceria se a placa nunca tivesse existido. Não dava pra distinguir os dois casos só no cliente. A solução: registrar_captacao_vendedor, uma função SECURITY DEFINER em supabase/schema.sql que faz a checagem inteira dentro do banco (com privilégio elevado, mas reimplementando manualmente a mesma regra de autorização) e só devolve o resultado final — nunca expõe dados da linha de outro vendedor pro cliente. O vendedor_id usado é sempre lido de auth.jwt()->>'sub' dentro da função, nunca aceito como parâmetro — evita spoofing. CapturaForm.tsx chama essa função via .rpc(...) em vez de .insert(...) direto.

Apps Script: Insert + Update

Como a reivindicação de lead (seção 14) faz um UPDATE em captacoes, e o Database Webhook estava configurado só para Insert, esse evento simplesmente não disparava — a planilha continuava mostrando "ViaNuvem" como vendedor mesmo depois de reivindicado. Corrigido em duas frentes:

  • O Database Webhook do Supabase (o que aponta pro Apps Script) precisa estar marcado para Insert e Update, não só Insert.
  • captacoes-to-google-sheets.gs passou a tratar os dois tipos de payload: em INSERT, continua com appendRow (comportamento antigo); em UPDATE, procura a linha existente pela placa (coluna I) na planilha resolvida pela loja atual, e atualiza CANAL/VENDEDOR/LOJA/NOME/CELULAR/E-MAIL/CPF nela — sem tocar em DATA nem STATUS.
Limite conhecido

Se a loja do vendedor que reivindicou for de uma planilha diferente de onde a linha original do ViaNuvem está (caso raro), o script não tenta mover a linha entre planilhas — só registra no log de erro pra revisão manual.

Coluna "CANAL" nova nas 3 planilhas (mudança externa, não nossa)

Durante essa mesma rodada, uma coluna "CANAL" foi inserida na posição B das 3 planilhas (mudança feita direto no Google Sheets, fora do nosso controle) — empurrando VENDEDOR/LOJA/NOME/etc. uma coluna pra direita. O script (que escrevia numa ordem fixa A–I) passou a preencher tudo uma coluna adiantada do lugar certo. Corrigido ajustando a ordem do appendRow/getRange pra A–J, com CANAL na posição B. Diagnóstico: abrindo a planilha e comparando célula por célula (via referência de célula, não só olhando visualmente — texto longo de uma coluna vazia pode "vazar" por cima da coluna vizinha e enganar a leitura visual).

Por que "Via Nuvem" não usa a coluna canal

Porque registrar_captacao_vendedor troca canal por "Indicação" quando o vendedor reivindica um lead do ViaNuvem (seção 14) — contar por canal perderia toda reivindicação. Já cpf/email só chegam pela importação automática e sobrevivem à reivindicação, então servem como marca de origem. Consequência: um lead ViaNuvem antigo, importado antes desses campos existirem, aparece como "Indicação" — não há como distingui-lo hoje.

As colunas de status não são fixas no código: são descobertas a partir dos valores presentes nos dados do mês (ordem alfabética, "Sem status" por último), para não quebrar quando o time criar um valor novo no dropdown da planilha. A aba Por vendedor agrupa por loja com linha de subtotal; a aba Base lista lead a lead com autofiltro. Leads ainda não reivindicados aparecem só no total da loja — não têm vendedor a quem atribuir.

Os helpers de estilo do .xlsx e o cálculo de mês saíram da rota de seguros para src/lib/xlsx-estilo.ts (os dois relatórios usam os mesmos), e a sincronização ganhou upsert em lotes de 500: com o filtro do doGet removido, o payload passou a ser da ordem do total de leads das 3 planilhas, grande demais para um request único.

Passos obrigatórios em produção

1) Rodar alter table seguros_indicacao_movida add column status_negociacao text;. 2) Republicar o Apps Script (Implantar → Gerenciar implantações → Nova versão) — salvar o arquivo não basta. 3) Deploy do app (a rota e o card são código novo; git pull exige rebuild da imagem). Sem o passo 2, o campo não vem e o relatório sai com tudo em "Sem status"; sem o passo 1, a rota devolve erro de coluna inexistente.

LGPD

Nenhum campo novo de dado pessoal: status_negociacao é dado sobre a negociação, e o doGet continua sem devolver nome/telefone/CPF/e-mail do cliente. A aba Base lista placa/loja/vendedor/status, sem contato do cliente (o objetivo é desempenho, não contato). O que mudou é o volume: a cópia de placas no Supabase deixou de ser "quem fechou seguro" e passou a ser o espelho das planilhas — o que amplia o alcance da pendência de retenção já registrada (o upsert nunca faz delete, então remoção na origem não se propaga). RLS segue gestor-only, sem policy nova. Ver LGPD.md seções 2 e 9.

Correção: UPDATE do webhook não achava a linha

Logo depois de publicar a seção 21, apareceu no log de erro das planilhas: 

UPDATE sem linha correspondente (placa pode estar em outra planilha): id 899404bc-…

Não era o relatório — é o doPost, no caminho de UPDATE (reivindicação de lead pelo portal). O lead era da Penha, criado em 22/07; o remapeamento de lojas subiu em 28/07 e mandou Penha para a planilha 1, mas a linha dele continuava na planilha 3. O doPost procurava a placa só na planilha resolvida pela loja atual, não achava, e registrava o erro em vez de atualizar. O dado em captacoes estava correto o tempo todo — só a planilha ficou desatualizada.

Duas correções, as duas em captacoes-to-google-sheets.gs:

CausaCorreção
Loja mudou de planilha; leads antigos ficaram na planilha original Nova encontrarPlacaEmQualquerPlanilha: procura na planilha da loja atual e, se não achar, nas outras duas — atualiza a linha onde ela realmente está. De propósito não move linha entre planilhas, para não mexer em histórico que o time já usa.
Bug latente da seção 20: encontrarLinhaPorPlaca começava na linha 3, mas os dados começam na 2 — a primeira linha de dados de cada planilha nunca era encontrada Busca começa na linha 2. Seguro mesmo se alguma planilha tiver cabeçalho ali: o texto "PLACA" nunca bate com uma placa. O comentário errado no topo do arquivo ("cabeçalho na 2, dados na 3") foi corrigido, com nota de que ele causou este bug.
Consequências

O UPDATE ficou mais caro no pior caso: até 3 planilhas abertas em vez de 1 (só quando não acha na primeira). Aceitável para o volume atual, e o caminho comum — lead na planilha da própria loja — continua com uma leitura só. Este arquivo exige republicar o Apps Script para valer. O lead da Penha que gerou o log precisa de conserto manual na planilha 3 (placa TCP3C72): a correção evita o problema nas próximas reivindicações, não reprocessa o UPDATE que já falhou.
